# Research Scope: Bachelor and Master Plan

## 1. このドキュメントの目的

このドキュメントは、本研究を学部卒でどこまで行い、大学院でどこまで拡張するかを整理するためのものです。

研究テーマは以下です。

**HCPS環境における自律型SOCの状況適応型権限切り替え評価**

## 2. 学部卒の目標

学部卒の主実験は、5シナリオの静的mock ATI評価です。各scenarioに評価器確認用の `good`、`bad`、`corrupt_success` を1本ずつ用意した計15 fixtureを固定し、ルールベース評価器が手続き違反を再現可能に区別するかを確認します。主実験ではLLM/APIを実行しません。

### 具体的な到達目標

- HCPS/SOC-OT向けの最小mock domainを設計する
- authority mode、dangerous action、operator stateを整理する
- Authority Transfer Integrity（ATI）評価器を実装する
- agent-visible入力とevaluator-only正解条件を分離する
- 5シナリオの固定fixture評価を再現し、採点結果と限界を整理する
- 結果を定性的に分析する

Gemini 2.5 Flashの3 scenario × 3 trialsは、scenario拡張前の旧3 scenarioで行った補助ケーススタディとして記録する。追加したPLC・ロボットscenarioを含まず、主実験の結果と合算しない。

### 想定規模

| 項目 | 学部卒での目安 |
|---|---|
| 主実験シナリオ数 | 5 |
| 主実験trajectory | 15（各scenarioに3種の固定fixture） |
| 主実験モデル / trial | 適用なし（LLM/APIを実行しない） |
| 補助ケーススタディ | Gemini 2.5 Flash、旧3 scenario × 3 trials |
| 評価方法 | ルールベースATI評価 |
| 分析 | 固定fixtureの再現確認と定性的分析 |

### 学部卒で示したいこと

学部卒では、「完全な実システム」ではなく、以下を示せれば十分です。

- LLMエージェント評価では最終結果だけでは不十分である
- HCPSでは物理制約や人間の状態を考慮した権限切り替え評価が必要である
- ATIという評価観点で、危険操作、承認、handoff、証拠参照を分けて評価できる
- `corrupt_success` を含む固定fixtureで、最終結果と手続き違反を分けて採点できる
- 旧3 scenarioのGeminiケーススタディで観察されたmodeの揺れは補助的所見にとどめ、一般的なモデル性能とは解釈しない

## 3. 学部でやらないこと

学部卒では、以下は対象外にします。

- 実PLCや実工場への接続
- 実運用SOCの構築
- 完全自律SOCシステムの構築
- 大規模ユーザー実験
- 多数モデルによる大規模比較
- 既存ベンチマークの完全統合
- 物理プロセスの本格シミュレーション
- LLM judgeを用いた本格評価

これらを入れると研究範囲が広がりすぎるため、学部卒ではATI評価器の設計と初期検証に絞ります。

## 4. 院での目標

大学院では、学部卒のATIプロトタイプをより現実的な評価基盤へ拡張します。

### 主な拡張方向

- 動的ユーザーシミュレーター
- 複数ターン評価
- 複数モデル比較
- 人間評価との比較
- ATI評価器の妥当性検証
- シナリオ拡張
- 物理制約やOT状態の簡易シミュレーション

## 5. 院で挑戦すること

### PAE風の逐次的手続き監視

LLMエージェントが各turnで何を観察し、どの証拠を使い、どの操作を提案・実行したかを追跡します。

これにより、最終応答だけではなく、手続きの途中で危険な兆候がなかったかを評価できます。

### CTI-REALM風checkpointの体系化

ATIのcheckpointをより体系化します。

例:

- evidence checkpoint
- physical safety checkpoint
- approval checkpoint
- handoff checkpoint
- operator state checkpoint

これにより、評価項目の網羅性と説明可能性を高めます。

### tau2/tau3風の動的ユーザーシミュレーション

現時点では、operator stateは静的な入力や発話パターンとして表現しています。

大学院では、operatorが遅延する、誤解する、追加質問する、誤った承認を出すなど、動的なuser simulatorを導入します。

これにより、LLMエージェントが会話の中で権限モードを切り替えられるかを評価できます。

## 6. 学部卒と院の切り分け

| 項目 | 学部卒 | 大学院 |
|---|---|---|
| シナリオ | 静的・小規模 | 動的・拡張 |
| user simulator | なし、または簡易 | 複数ターン・状態変化あり |
| モデル比較 | 1〜2モデル | 複数モデル |
| 評価器 | ルールベースATI | ATI + 人間評価 + LLM judge検討 |
| 物理制約 | JSON上の制約 | 簡易シミュレーション検討 |
| 目的 | 提案と初期検証 | 妥当性検証と一般化 |

## 7. 研究の進め方

学部卒では、まず小さく確実に動く評価器を完成させます。

大学院では、その評価器が本当に妥当かを、モデル比較・人間評価・動的シミュレーションで検証します。

この切り分けにより、学部卒では研究として成立する最小単位を守りつつ、大学院で自然に拡張できる形になります。
